AeroTwin-Edge — POC BUILD RUNBOOK
Problem statement: EDGE AI FOR DIGITAL TWIN-ENABLED MRO.
The POC = ONE unbroken chain (sense -> twin -> predict -> DECIDE -> fleet -> agent),
all offline. Real where it's cheap to be real; seeded where real would cost days.

==================================================================
THE ONE FEATURE TO NAIL (judges reward this above all)
==================================================================
The TWIN's condition-based DECISION and FLEET RISK BOARD: per-tail health index +
remaining-useful-life -> "PULL this tail's inspection FORWARD / SAFE TO EXTEND that
one / GROUND this one", ranked across the fleet against the calendar baseline.
THAT is the digital twin — the thing a defect detector on its own can never be. The
sensor chain (px->mm->SRM-grade->cycles-to-limit) is the bridge that feeds it; the
twin brain is the payoff. If everything else were mocked, the twin turning a fleet
of findings into a scheduling call still carries the submission.

==================================================================
RUN THE REAL REPO (this is what the video shows)
==================================================================
  python -m src.pipeline --seed        # reset + seed a deterministic 4-tail fleet
  uvicorn src.l1_twin.app:app --port 8000   # -> fleet risk board + per-tail twin
  #   or, zero web stack:  python tools/render_dashboard.py  (static HTML screenshot)
  python -m src.l1_twin.twin           # twin self-check (health/RUL/CBM math)
  python -m src.pipeline --image panel.jpg --real   # real detector once trained
The fleet board (1 grounded, 2 pull-forward, 1 safe-to-extend) is the headline image.

==================================================================
A. REAL CORE  (~4-6 hrs, one ML person)  -> detect_and_size.py
==================================================================
1. pip install ultralytics opencv-contrib-python numpy matplotlib
   (opencv-contrib-python is required for cv2.aruco; needs OpenCV >= 4.7.)
2. Print an ArUco marker (DICT_4X4_50, id 0), known edge length (default 50 mm).
   MEASURE the printed marker with calipers and set ARUCO_MARKER_MM accordingly —
   that is your one real-world calibration knob.
3. Collect ~5 crack images with the marker in frame: SDNET2018 / NEU-DET, or real
   photos of a scored aluminium panel. (Public sets are fine for the POC.)
4. Self-check the sizing logic with no model/images needed:
       python detect_and_size.py --selftest        # prints "selftest ok"
5. Run the full pipeline on an image:
       python detect_and_size.py panel_with_aruco.jpg
   Output, e.g.:  crack 8.0 mm — MAJOR — 67% of 12 mm SRM limit
   (Pretrained yolov8n-seg.pt is generic; for a crisp crack mask, optionally
   fine-tune 1-2 hrs on SDNET2018 and point YOLO() at your weights.)

==================================================================
B. REAL-BUT-SEEDED SHELL  (~4-6 hrs)  -> twin_console.py  (Streamlit)

==================================================================
NOTE ON THE "~40 CYCLES" FIGURE  (read before recording)
==================================================================
The script/slides say the crack crosses the 12 mm limit in ~40 flight cycles, and
twin_console.py uses PROJECTED_CYCLES = 40 so the chart matches. Be aware: your own
problem-statement Annex C implies a few HUNDRED cycles for an 8->12 mm growth band.
40 cycles is a deliberately aggressive "fast-growth" scenario. Two honest options:
  (a) Keep 40 and frame it as a rapidly-progressing defect (e.g. post lightning-
      strike) — then say that in the narration.
  (b) Raise it (e.g. ~300) to match standard DTA — then update VIDEO_SCRIPT.txt,
      SLIDE_BLUEPRINT.txt (slides 4 & 8) and PROJECTED_CYCLES together.
Whichever you pick: the number you SAY, the chart, and the slides must all agree.

==================================================================
VERIFICATION (before you record)
==================================================================
1. Offline: disconnect network, run detect_and_size.py on the 5 images -> sane mm
   for each. If it needs the network, the edge story is dead — fix first.

3. Progression: confirm the projected limit-crossing is monotonic and plausible.
4. Agent guardrail: query a defect with no SRM excerpt -> it must refuse/escalate,
