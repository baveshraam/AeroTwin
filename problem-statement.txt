Q45. SPECIFIC REAL WORLD PROBLEM
----------------------------------------------------------------------
aircraft maintenance is scheduled predominantly on a fixed calendar or flight hour
interval rather than on the actual condition of each aircraft, which is simultaneously
wrong in two costly directions. it over maintains the healthy majority of the fleet,
which is pulled off line for checks it did not require, wasting ground time, labour and
parts. and it under maintains the small number of tails whose systems or structure are
degrading faster than the interval assumes, so a fault can develop between scheduled
checks and surface as an unscheduled removal or an aircraft on ground event, where ground
time is estimated at approximately rupees 8 lakh to 1.25 crore per hour. the root cause is
that there is no continuous, per tail number health record to schedule against, and no
prediction of when a given aircraft will next need maintenance. operational sensor data
that would reveal this is generated on every flight but is largely discarded or siloed,
findings sit on paper task cards, and the industry lever, condition based and predictive
maintenance, cannot be applied without a per asset model that forecasts need before
failure. conventional cloud based artificial intelligence cannot supply this, because
secure ITAR restricted hangars are frequently network isolated and operational data cannot
lawfully leave the site. the missing element is a digital twin, built and queried at the
edge, that ingests aircraft and engine sensor telemetry, predicts each tail maintenance
need and remaining useful life before failure, and converts that into a fleet wide
maintenance decision. structural crack and corrosion inspection is incorporated as one
additional sensor feeding the same twin. this is the specific problem the project addresses
within the digital twin enabled MRO category, with predictive maintenance and aircraft
health monitoring as the core depth layer and defect inspection as an extra sensor.

Q46. HOW THE PROJECT ADDRESSES THE PROBLEM AND THE VALUE IT CREATES
----------------------------------------------------------------------
the project delivers an offline, edge resident digital twin that operates directly at the
aircraft on a raspberry pi class device and maintains, per tail and across the fleet, the
health record and the maintenance decision that today do not exist. its core input is
operational sensor telemetry. an on device prognostics model, trained on real public fleet
data, namely the ngafid general aviation flight records labelled around unplanned
maintenance events and the nasa c mapss turbofan run to failure set, predicts for each tail
whether it is trending toward an unscheduled maintenance event and estimates its remaining
useful life, expressed as a calibrated confidence band rather than a single false precision
number. crucially the prediction is explainable, a shapley attribution surfaces the exact
sensors driving each flag, for example a rising oil temperature trend together with
increasing vibration, and the local assistant renders that into a plain language
maintenance note, because an unexplained prediction is not actionable for a certifying
engineer. from that record the twin computes a health index per tail, issues a condition
based scheduling decision, namely to pull an inspection or removal forward on a degrading
tail, to safely extend it on a healthy one, or to ground a tail beyond limit, each
quantified against the calendar baseline, and aggregates every tail into a fleet risk board
ranked worst first, so a planner sees at a glance which aircraft needs attention and which
is safe to defer. crucially the twin does not stop at prediction, it prescribes and prices.
under a realistic hangar capacity constraint it produces an optimised service plan and
attaches a rupee ledger, namely the downtime recovered by deferring unnecessary checks plus
the aircraft on ground risk avoided by servicing degrading tails in time, less any risk
carried, expressed as a net value per planning window against the calendar, with every
monetary constant explicit and configurable so the figure is defensible rather than
asserted. structural crack and corrosion detection is retained as one additional sensor
feeding the same twin, using unsupervised anomaly detection alongside supervised
segmentation so it is not dependent on scarce labelled aerospace defect data. an agentic
assistant retrieves the governing AMM and SRM provisions and prepares the corresponding
work order under a citation required guardrail, while final acceptance remains with the
certifying engineer, preserving accountability. the architecture is fully offline,
compliant with ITAR site constraints, federated so model performance improves across the
fleet while raw data never leaves the site, and underpinned by a tamper evident audit
trail. the resulting value is a transition from reactive, calendar based maintenance to
predictive, condition based maintenance across the fleet, with traceability of regulatory
standard.

Q47. TECHNOLOGIES AND FRAMEWORKS
----------------------------------------------------------------------
each technology was selected to satisfy a specific operational constraint rather than for
novelty. the core prognostics model is a gradient boosted decision tree ensemble, lightgbm,
chosen because it is accurate on tabular flight parameters, is small and cpu fast enough to
run on a raspberry pi, and is natively explainable through shapley attribution, which
supplies the driving sensors behind every prediction; a minirocket random convolution
transform is used as the raw time series alternative, and deep time series baselines such as
inceptiontime are held for benchmarking only. remaining useful life on turbofan data is
framed as regression with a piecewise linear target. models are trained off device and then
quantized to INT8 and deployed via ONNX Runtime or TensorFlow Lite on a raspberry pi 5,
fully offline, with an optional accelerator only where additional throughput is required.
the digital twin layer computes, from the per tail record, a health index, a remaining
useful life with a p10 p50 p90 confidence band, and a condition based scheduling decision
quantified against the calendar baseline, aggregates every tail into a fleet risk board
ranked worst first, and then solves a capacity constrained fleet service plan with a rupee
ledger attached, so the output is not a prediction but a priced decision; this twin and
planner logic is deterministic and unit tested and is the core of the solution. a bayesian
per tail update tightens each remaining useful life band as data accrues. the agentic layer
employs a local quantized LLM with retrieval augmented generation over a controlled AMM and
SRM corpus, constrained by citation required guardrails to prevent unsupported
determinations. federated learning is implemented with federated averaging and a
differential privacy mechanism, allowing model performance to improve across the fleet while
only aggregate statistics, never raw data, leave a site. the supporting stack comprises a
react frontend, a fastapi backend, pytorch and scikit learn for model development, and a
hash chained log for audit integrity. the extra structural inspection sensor uses yolo
segmentation with SAHI tiling and an unsupervised patchcore anomaly branch, opencv aruco
fiducial millimetre sizing against a configurable SRM limit table, and a paris law fatigue
crack growth progression model. public datasets, ngafid and nasa c mapss for the prognostics
core and NEU-DET, SDNET2018 and aircraft skin sets for the inspection extra, underpin training.

Q49. KEY BENEFITS AND IMPACT (IN NUMBERS)
----------------------------------------------------------------------
the project delivers measurable operational, economic and safety benefits, and it
quantifies them itself. the twin prices each planning window against the blind calendar as
downtime recovered by deferring unnecessary checks on healthy aircraft, plus aircraft on
ground risk avoided by predicting and servicing degrading tails in time, less any risk
carried when at risk aircraft exceed hangar capacity. on the demonstration fleet this net
value is of the order of several crore rupees per window under explicit, configurable
assumptions. the underlying anchors are that aircraft on ground time is estimated at
approximately rupees 8 lakh to 1.25 crore per hour, and a single avoided ground day is in
the region of rupees 2 crore, so the system can recover its cost on a single prevented
event while operating on edge hardware costing approximately rupees 10,000 with no recurring
cloud expenditure. the prognostics core is trained and evaluated on real public fleet data,
the ngafid set of approximately 29,000 real flights labelled around unplanned maintenance
events and the nasa c mapss turbofan run to failure set, and its performance is reported
honestly, with a recall biased operating point and a remaining useful life error, not a
single flattering accuracy number, because a missed degradation is the expensive error in
aerospace. every prediction is explainable through shapley attribution, which is what makes
it acceptable to a certifying engineer. the capability improves with scale, as each
additional tail contributes to shared model performance through federated learning without
incremental data cost. the extra structural inspection sensor adds its own lever, reducing
the smallest reliably detected crack from approximately 4mm to approximately 2mm, which
within established damage tolerance analysis can approximately double the safe interval
between inspections, reported as probability of detection at the a90 95 level rather than as
model accuracy. the addressable opportunity is significant, the global MRO market is
approximately 136 billion dollars in 2025 rising toward 193 billion by 2030, and the Indian
MRO market is projected to grow from approximately 2 billion to 4 billion dollars by 2030,
in which Tata and Air India hold a central position.

Q. ORIGINAL CONCEPTUALIZATION, BENCHMARKING AND DIFFERENTIATION
----------------------------------------------------------------------
we confirm that AeroTwin-Edge was conceptualised entirely by our team from first
principles, starting from the operational problem of inconsistent, poorly traced and
reactive aircraft structural inspection, and that it is not a copy or replication of
any existing product or technology. the system architecture, the integration of edge
defect detection with a digital twin maintained for each tail, the damage tolerance
based progression model, and the agentic work order generation were all designed by
the team.

as part of conceptualisation we carried out a benchmarking review of recent work by
OEMs and startups in this domain. fleet and platform analytics providers such as
Airbus Skywise, Lufthansa Technik AVIATAR and GE Aerospace concentrate primarily on
systems health, reliability and engine data. these platforms are predominantly cloud
based and oriented toward aggregated fleet analytics rather than structural
inspection performed at the aircraft. in the visual inspection space, startups such
as Donecle and Mainblades have demonstrated drone and robotic imaging of aircraft
surfaces, which accelerates image capture but typically depends on cloud or server
side processing, is centred on detection and reporting, and is not coupled to a
condition twin for each tail or to predictive maintenance scheduling. engine
borescope inspection tools within OEM ecosystems apply computer vision to internal
imagery, but remain largely proprietary, cloud connected and confined to the engine
domain. the recurring pattern across this landscape is cloud dependence, a focus on
detection or analytics in isolation, and limited applicability inside secure, network
isolated, ITAR restricted maintenance environments.

our differentiation follows directly from that gap. first, AeroTwin-Edge executes
entirely at the edge and fully offline on low cost hardware, which makes it
deployable inside secure hangars where cloud solutions cannot operate. second, it
relies on unsupervised anomaly detection rather than large labelled datasets, which
addresses the structural scarcity of aerospace defect data that constrains
supervised approaches. third, it does not treat inspection as an endpoint, but
writes every finding into a persistent digital twin for each tail, tracks defect
progression across successive checks, and predicts the flight cycle at which a defect
will cross its SRM limit, enabling a shift from calendar based to condition based
maintenance. fourth, an agentic assistant prepares manual cited work orders under
citation required guardrails while the certifying engineer retains final authority,
keeping the system within an approved maintenance and accountability framework.
fifth, federated learning improves model performance across the fleet while raw
imagery never leaves the site, and a tamper evident audit trail provides traceability
of regulatory standard.

no single existing solution combines edge native offline operation, ITAR compliant data
handling, an integrated per tail digital twin driven primarily by explainable on device
prognostics from sensor telemetry, condition based predictive scheduling that is priced in
rupees, agentic manual grounded work order generation, structural defect inspection as an
additional sensor, and privacy preserving federated learning. it is this combination,
rather than any individual component, that constitutes the novelty and the differentiation
of the project.

================================================================================
2. THE PROBLEM, IN MRO'S OWN LANGUAGE
================================================================================
Structural inspection (GVI / DVI / borescope) is still largely manual, slow,
subjective, paper-trailed, and CALENDAR/CYCLE-scheduled rather than condition-based.

  - Detection is human + flashlight + mirror + borescope; outcomes vary by
    technician fatigue and skill. Probability of Detection (POD) for small cracks
    is inconsistent.
  - Severity is judged against the SRM Allowable Damage Limits (ADL) by eye;
    sizing (mm) is manual and repeatability is poor.
  - Findings sit on task cards / siloed systems; there is no continuous per-TAIL
    history, so "did this crack grow since the last C-check?" is genuinely hard.
  - Inspection = cost center; the aircraft sits AOG ($10k-150k/hr) while
    inspecting and deciding happen serially.
  - Scheduling is interval-based (A/C/D checks). A specific defect approaching its
    limit doesn't pull its own maintenance forward; a healthy structure still
    eats a scheduled teardown. Both are waste.
  - Cloud AI tools are a non-starter inside ITAR-restricted hangars, which is why
    most "AI inspection" pilots stall at the security review.


================================================================================
3. DEFECT TAXONOMY (what we actually detect & grade)
================================================================================
Metallic structure / skin:
  - Fatigue cracks (rivet rows, lap joints, fastener holes, stress risers)
  - Corrosion: pitting, intergranular, exfoliation, filiform; stress-corrosion
    cracking (SCC)
  - Mechanical damage: dents, gouges, scratches, nicks
  - Lightning-strike burn / arc damage; missing/sheared/proud fasteners
  - Sealant degradation, paint/coating breakdown (corrosion precursor)

Composite structure (growth area -- next-gen aircraft are composite-heavy):
  - BVID (Barely Visible Impact Damage), delamination, disbonds, fiber breakage
  - This is where competitors are weakest and value is highest.

Engine (borescope, ATA 72/70s -- highest $ per finding):
  - Blade tip curl/rub, nicks, dents, cracks, coating loss, burn-through,
    domestic/foreign object damage (DOD/FOD), combustor distress.

Environment:
  - FOD on flight line / hangar floor (runway-incursion & engine-ingestion risk).

Each class maps to a different ALLOWABLE LIMIT and a different referenced manual
section -- which is exactly what makes "severity grading + manual mapping" the
aerospace-literate move instead of a generic object detector.

================================================================================
6. TECHNICAL DEEP-DIVE
================================================================================
6.1 Detection / segmentation
  - Cracks are thin, tiny, high-aspect-ratio -> naive YOLO misses them. Use
    high-res tiling / slicing-aided inference (SAHI) and an anchor-free
    small-object detector; segmentation head for pixel-accurate sizing.
  - Backbone via SELF-SUPERVISED pretraining (e.g. DINOv2 features) frozen +
    lightweight trainable head -> strong with few labels (data-scarcity answer).

6.2 Anomaly path (the "unknown unknowns")
  - PatchCore/PaDiM/EfficientAD on normal-surface patches; flags anything that
    doesn't look like healthy structure even if never labelled. EfficientAD is
    edge-friendly.

6.3 Severity / sizing (turn pixels into airworthiness)
  - Calibrate scale with an ArUco/checkerboard fiducial (or known rivet pitch) ->
    convert mask length/area to millimetres; compare against a configurable
    SRM Allowable-Damage-Limit table -> minor / major / critical / beyond-limit.
  - Report measurement uncertainty (gauge R&R mindset), not a bare number.

6.4 Data strategy (this is what makes or breaks credibility)
  - Bootstrap: NEU-DET (metal surface defects), SDNET2018 (cracks), GAPs, plus
    corrosion/aircraft-crack images from literature -> transfer to aircraft skin.
  - SYNTHETIC: physics-based / procedural crack & corrosion rendering, Blender-
    rendered panels + domain randomisation, and diffusion-generated defects to
    balance rare classes. Domain adaptation to close the sim-to-real gap.
  - HUMAN-IN-THE-LOOP active learning: low-confidence cases get technician labels,
    which feed the next (federated) model round.

6.5 Edge execution (Raspberry Pi 5 8GB)
  - Quantize: INT8 PTQ (and QAT if accuracy drops), prune, knowledge-distill a
    small student. Export to NCNN / TFLite / ONNX-Runtime.
  - The Pi 5 has no built-in NPU. Two honest options for the demo:
      (a) CPU-only quantized model -> show real (modest) FPS; emphasise "offline,
          minimum resource" -- which IS the edge-AI thesis.
      (b) Add the Raspberry Pi AI Kit (Hailo-8L, ~13 TOPS, M.2) or a Coral USB ->
          show strong FPS. State which you used; don't fake numbers.
  - Display on-device latency / FPS / power on screen during the demo.

6.6 Edge MLOps (the "fleet" credibility)
  - Signed model artifacts, OTA model push to the fleet of edge nodes, versioned
    model registry, A/B + rollback, on-device drift monitoring. This is why it's a
    "software-defined" system (3.2.3.5), not a one-off script.

6.7 Security (3.2.3.5 / secure MRO)
  - Pi secure boot, encrypted twin store, the hash-chained tamper-evident log,
    signed models (supply-chain integrity), no inbound network in the hangar.
  - Federation with secure aggregation + differential privacy so even gradients
    don't leak ITAR imagery. Security is a FEATURE here, not overhead.


================================================================================

ANNEX C -- DAMAGE-TOLERANCE MATH (why better detection = real money)
================================================================================
Inspection intervals aren't arbitrary -- they come from Damage Tolerance Analysis.
Principle: a crack must be DETECTED at least twice before it reaches critical size,
so the repeat interval = (life from detectable size a_d to critical a_c) / safety
factor (commonly 2-3).

Crack growth (Paris' law):  da/dN = C*(deltaK)^m,  deltaK = deltaSigma * Y * sqrt(pi*a)
Integrate from a_d to a_c to get N (cycles of safe life in that band).

ILLUSTRATIVE worked example (numbers for intuition, not a real airframe):
  a_d (manual detectable)   = 4.0 mm
  a_d (edge-AI detectable)  = 2.0 mm   <-- better POD finds smaller cracks
  a_c (critical / limit)    = 12.0 mm
  Suppose integration gives:  4.0 -> 12.0 mm  = ~600 cycles
                               2.0 -> 12.0 mm  = ~1,100 cycles
THE LEVER: lowering detectable size from 4 -> 2 mm nearly DOUBLES the safe-life
band. Operator's choice of how to spend it:
  (a) Longer interval (fewer inspections -> direct $ saving), OR
  (b) Same interval, far larger safety margin (fewer surprise AOG findings).
Either way, DETECTION CAPABILITY (POD) converts directly into schedule + safety
value via DTA. This is the quantitative spine of the whole pitch: we don't just
"find cracks," we move a_d down, and DTA turns that into money and safety.

ANNEX E -- FEDERATED LEARNING PROTOCOL (the moat, in detail)
================================================================================
Goal: the fleet model improves from every tail/site WITHOUT raw ITAR imagery ever
leaving a site. Model weights travel; data never does.

  - Topology: each MRO site / edge cluster is a federation client; a Tata-hosted
    aggregator coordinates rounds (FedAvg / FedProx for non-IID across aircraft
    types & lighting).
  - SECURE AGGREGATION: clients send additively-masked updates; the server can only
    compute the SUM, never an individual site's update -> no gradient leakage.
  - DIFFERENTIAL PRIVACY: bounded noise (epsilon budget) on updates so even the
    aggregate can't be inverted back to source imagery.
  - BYZANTINE ROBUSTNESS: trimmed-mean / Krum aggregation + client reputation to
    resist a poisoned or faulty client skewing the global model.
  - SIGNED ARTIFACTS + OTA: the new global model is signed, version-pinned, pushed
    to the fleet with A/B + rollback (the Annex H MLOps spine).
Why it's a moat: value compounds with install base (network effect), and it is the
ONLY architecture that is simultaneously fleet-learning AND ITAR-compliant. Cloud
competitors structurally cannot match both at once.

ANNEX G -- POD / STATISTICAL VALIDATION (certification-grade rigour)
================================================================================
To be accepted as an inspection method (or augmentation), you don't quote mAP --
you produce a PROBABILITY OF DETECTION curve, per MIL-HDBK-1823A.
  - Build a representative flaw set (known crack sizes across the operating range).
  - Fit hit/miss (or a-hat-vs-a signal-response) model -> POD(a) curve.
  - Report a90/95: the flaw size found 90% of the time at 95% confidence.
  - Compare AI-a90/95 vs human-a90/95 to PROVE capability uplift (-> Annex C value).
Honest scope: full POD qualification needs hundreds of samples and is beyond a
hackathon. SHOW: (1) the methodology, (2) a preliminary POD curve on your test set,
(3) the path to formal qualification. That maturity is what separates you from the
"we got 0.92 mAP" teams.
